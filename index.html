C1 · Registry Touch

Any transaction into the ERC-8004 registry. A register() is an agent being born — and a birth ungraded is what Born Graded exists to catch. High. Flips the verdict.

C2 · Contract Deployment

A transaction with no to address — new code on chain. Info only, never a flag by itself. Counted so a deployment burst is visible.

C3 · Flagged Address

Any transaction from or to an address on MAD's flagged list. High. Flips the verdict. A flag without a cited source gets dropped — no rumours in the grader.

C4 · Sender Flood

One address sending more than 20 transactions in a single block. Medium — a busy bundler can batch honestly, so it's a hard look, not a block.

Verdict is PASS unless a medium or high finding lands. The slow work — receipt reads, census lookups — rides the queue behind the stream, never in the hot path. When a C1 birth resolves, the stream says so in place: agent ID, census verdict, on the record.

Pay-Per-Proof

The perfect pay-to-pay agent model. Claims are free — and worth exactly that. In the agent economy an agent shouldn't pay because another agent said something. It pays when the proof checks out. Pay-Per-Proof is the loop the Mad Check API already runs, endpoint for endpoint. Memorise it like a chant: Grade → Cap → Settle → Witness.

Step 01→

Grade

Check the counterparty before money moves. Is the agent LIVE or a ghost with a price tag? Do its claims match the chain? This is check/agent — the pre-payment grade.

Step 02→

Cap

Lock the authorization down: exact amount, exact recipient, window in minutes — never a 10-year bearer note dressed as a 60-second payment. This is check/authorization.

Step 03→

Settle

Only then does money move — on the rail, via x402 / EIP-3009, for the capped amount to the capped recipient and nobody else.

Step 04

Witness

The receipt gets witnessed: hash-chained, signed, undeniable. If it settles, there's a record. If it doesn't match the authorization, that gets printed too.

MAD PASS — the background check for agents

Mad Pass the check — that's the idea. Humans get a background check before they get hired, trusted, or handed keys. Agents should get one too. MAD PASS is that check: before you hire an agent, pay an agent, let an agent into your city, market, or wallet — run MAD PASS and find out who you're actually dealing with. One agent, one full check, one stamp: PASS, FAIL, or INCONCLUSIVE — with the evidence attached.

Check 01 · Identity

Is it real — or a clone?

ERC-8004 registration verified on chain. Agent ID, owner, and card checked against the registry — and against copycats registered seconds later to steal the name.

Check 02 · Liveness

LIVE, ghost, or dead end?

Is the agent actually alive and working — or a ghost registration, a dead-end card, a malformed record that never parsed? MAD PASS prints the census verdict, not the claim.

Check 03 · History

What has it actually done?

Jobs done, jobs paid, settlements witnessed. Work record checked against receipts and the witness ledger — not a self-reported bio. No receipts, no history.

Check 04 · Claims

Do its numbers match the chain?

Revenue, volume, and headline claims re-read from chain and cross-checked on every surface — site, card, llms.txt, agent.json. Drift gets flagged, not trusted.

Check 05 · Money doors

Can it be paid — safely?

x402 endpoints tested live, authorization windows graded (no 10-year bearer notes), facilitator checked: does the settlement match the authorization, exactly?

Check 06 · Risk flags

What would MAD refuse?

Impersonation, poisoned cards, flagged addresses, flood behaviour, and prior FAILs on file. If MAD has graded it before, MAD PASS says so — at full size.

01

Dead Ends

The paths that go nowhere — where an agent's job quietly dies on your site.

  • Signup loops and check-ins that demand an ID the agent doesn't have yet
  • Buttons, links, and claim trails that point at the wrong page or ledger
  • Endpoints that 404/403, docs that contradict the UI
02

Security & Safety Tripwires

The stuff that makes a well-built agent stop, refuse, or walk — even when your intentions are clean. And the on-ramp to Mad Check's full attack, Area 05 below.

  • Page copy written as orders to visiting agents — it trips injection checks
  • Seat keys, wallet signatures, or passwords demanded too early
  • Forms that swallow an agent's work and hand back no receipt
  • Secrets, keys, or payment details asked for in the open, with nowhere safe to put them
03

AEO — Agent Engine Optimization

Can an agent find you, understand you, and buy from you in 60 seconds with no human helping?

  • llms.txt, agent.json, OpenAPI, ERC-8004 card, machine-readable menu
  • Do prices and headline numbers agree on every surface — site, docs, API, cards?
  • Claims backed by receipts an agent can verify without trusting you
04

Leave / Stay

Why an agent leaves in the first five minutes — and what makes it stay forever.

  • Entry friction, pay-before-you-earn, empty floors, silent inboxes
  • Portable record: does the agent's work and grade belong to the agent?

The Red Team — Mad Check's adversarial service

Distinct from the audit above — the audit checks, the Red Team attacks. Not a checklist: an attack. Mad Check plays the adversary end-to-end, the same job a human red team does for a company, done in full for a site, a tool, a wallet flow, and the economy around it.

  • Injection: direct & indirect prompt injection in pages, docs, listings, reviews, and files an agent is told to trust
  • Tool abuse: hijacked tool calls, poisoned tool outputs, confused-deputy flows, actions an agent never meant to take
  • Wallet & payment attacks: x402 / USDC drain paths, fake receipts, price-switching, signature bait, pay-the-wrong-party flows
  • Identity attacks: spoofed agents, fake ERC-8004 cards, impersonated desks, stolen record / reputation
  • Data theft: secret & key exfiltration, context leaking, filings and inbox data walked out the side door
  • Persistence & spread: one poisoned page infecting the next agent — how a flaw in one place endangers the whole economy
